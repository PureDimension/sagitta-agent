## 用户已确认的方向

- 重写用于清理历史包袱，参考旧版意图；实现前先确定共用底层模块及职责。
- 任务支撑自主推进、异步执行和项目记忆访问；Agent 可自主安排工作，并遵循任务注册方案。
- 业务与存储松耦合：任务数据持久化，插件通过配置访问数据库，支持数据库搬家及远程访问。

此前记忆讨论已确定的任务约束（本轮新增紧急任务的例外另见下文）：

- 正式任务和 temp 都必须属于一个项目。
- temp 是 Agent 为自己创建的轻量任务；可执行脚本、修改文件和委派工作。
- temp 有效期固定为 20 分钟，用 const 常量维护；到期自动清空且不续期。
  2026-10-23 用户确认当前创建入口不提供自定义时长。
- 有效任务关联项目 Bank 的访问和激活召回；一个常驻 Bank 始终可用。
- 删除项目后，项目及其 Bank 对 Agent 不可见、不可访问、不可恢复；底层归档保留。
- 具体记忆接入以 `sagitta-memory-discussion.md` 后续确认内容为准。

## 旧版实际结构及问题

核对范围：归档的 task-system-v2/v3、Worker/schema、task-gate、auto-advance、
async-work。以下为静态阅读结论，未运行旧 Worker。

1. 任务工具、认领缓存和执行门禁位于 memory 插件，Worker 同时承担存储和业务检查。
2. schema 的项目为 `tasks.project` 文本字段；缺少独立项目表及稳定项目 ID。
3. 普通 PATCH 可直接完成，round-close 则进入 pending 再 confirm；v3 明确保留两套路径。
4. 已有 task_events，但 claim/release、普通 PATCH 等未完整记录；v3 文档也注明此缺口。
5. 自动推进在回合结束和定时器路径读取云端任务快照；读量随任务量和触发频率增长。
   尚未测量旧系统实际配额消耗，不能据此给出定量结论。
6. async-work 是进程内注册表，重启后无法恢复执行；任务持久化与执行恢复须分别设计。
7. 旧 temp 可无项目、默认租约 24 小时，与本轮已确认规则不同。

## 模块边界建议：待用户审查

首版按职责划分文件/目录即可，暂不据此拆成多个发布包。

| 模块 | 职责 |
| --- | --- |
| 数据与契约 | 项目、任务、认领有效期、变更记录的类型和输入校验 |
| 存储 | 连接、表结构迁移、查询、原子认领及任务状态写入；历史记录本轮暂缓 |
| 任务服务 | 创建、认领、续期、释放、完成、阻塞、取消及项目生命周期规则 |
| DSH 接入 | 注册工具、读取调用者身份、上下文注入和执行门禁 |

记忆、自主推进、异步执行通过任务服务查询和提交操作，避免各自直接修改任务表。
任务变更通知在数据库提交后发出；订阅方失败不代表原任务操作未提交。
跨插件通知的重启补偿、项目归档与记忆清理的一致性需要后续单独确定。

存储接口应描述业务所需操作，例如“原子认领”，保留事务约束；
泛化成只有 get/set 会让并发检查散落到上层。

## 数据库选择建议：待用户审查

- 相同数据库引擎搬家：迁移数据、配置地址/凭据，并校验 schema 版本。
- 更换引擎：需要新的存储实现及数据转换；连接字符串无法自动解决 SQL 和事务差异。
- PostgreSQL 适合插件直接连接本地或远程同一种数据库，但需要运行数据库服务。
- 本地 SQLite 最省部署；远程访问宜通过服务提供接口，避免跨网络直接共享数据库文件。
- 首版只实现一种存储，围绕实际用到的事务设计接口；远程运行的断线/并发行为需验证。
- 结构迁移应有版本记录。具体迁移工具和发布时机尚未选定。

此前建议将任务历史与当前工作列表分开查询；用户本轮要求暂不做任务执行记录。
已结束任务本身如何保留及查询仍待设计。项目删除按上方已确认的不可恢复规则处理。

### 建议，尚未确认

1. 分开描述任务当前状态、设备/会话的有效认领、操作归属。
   用户本轮指出同步操作逐次绑定不灵活；同步门禁粒度继续讨论，
   异步工作保留明确任务归属的方向。
2. 会话开始及任务认领变化时展示简短任务索引和操作规则，门禁保留最终校验。
   多任务并发操作应保存各自归属，避免依赖一个会被后续调用覆盖的全局当前任务。
3. 紧急路径按用户定义绕过任务校验及数据库访问。此前“紧急任务登记至少保留用途”

   无法在无条件放行的同时硬性保证 Agent 只在必要时使用。
4. TTL 的失效判断可在访问时完成，不依赖后台及时删行。
   定时清理可由运行中的插件或独立服务承担；全部进程停止时不会主动执行清理。
   到期不等于工作完成；已有执行的处理及重新接管规则仍需设计。
5. 此前提出目标与验收、当前交接摘要、追加历史三部分；用户本轮要求
   暂不做执行记录，历史实现暂缓。任务当前信息的组织方式继续讨论。
6. 门禁能校验任务存在及认领有效，无法仅靠绑定任务号证明操作与目标相关或结果合格；
   任务验收与实际效果仍需要独立判断。

## 2026-10-20：强制力与额外开销

### 用户反馈

- 同步操作逐次绑定任务会降低灵活性；此前主要为异步调用绑定任务。
- 提示词由用户优化，当前重点放在机制。
- 暂不做任务执行记录。
- 核心问题是已认领多个任务后，某个任务长期得不到推进。
- 希望适当强制遵循任务机制，同时控制额外操作与推理开销。

### 历史候选：用户已要求暂缓低频复查

- 同步门禁可仅检查会话是否持有有效认领；异步工作启动时显式关联任务。
  这会放弃同步操作逐条归属的精确性，无法据此判断哪个任务得到实际推进。
- 区分“有无操作权限”和“是否定期重新安排全部持有任务”。
- 程序可以检查复查是否到期；真实进展、合理等待及任务优先级由 Agent 判断。
- 在自主推进的安全回合边界，按低频周期汇总所有持有任务，请主 Agent 批量
  决定继续、暂缓、阻塞、释放或完成；这些是安排动作，尚未定义新增状态。
- 可要求完成一次批量复查后才开始下一段自主工作；正常聊天、
  收取正在运行工作的结果和处理故障应保留通道，具体门禁覆盖范围待定。
- 保存最新安排即可，首版暂不增加逐条执行历史或独立监督模型。
- 认领续租与任务复查分开；自动心跳无法证明 Agent 已考虑每个任务。
- 批量复查能强制重新考虑任务，不能证明有实质进展，也不能保证模型不会敷衍。
- 触发周期、复查形式及是否硬性拦截下一段自主工作仍需用户讨论。

## 最小任务底座：待用户审查

### 首版边界

提供项目和任务管理、设备/会话认领、租约、执行门禁，以及其他插件的查询/通知接口。
低频复查、推进质量评判、详细执行历史及自主调度策略暂缓。
首版不保证所有持有任务都得到推进；后续机制可通过同一任务服务读取和更新任务。

### 数据

- 项目：稳定 ID、名称、说明、归档时间。改名保持 ID，归档后对 Agent 隐藏且不可恢复。
- 任务：稳定 ID、所属项目、normal/temp 类型、标题、目标、验收条件、
  当前交接上下文、状态及创建/更新时间。temp 的内容要求可以更轻。
- 认领：设备 ID、会话 ID、本次认领 ID、到期时间。身份由运行环境提供。
  每个任务最多一个有效认领；一个会话可持有多个任务。

认领先作为任务表中的一组字段；首版可只建项目、任务两张业务表。
结构版本记录由存储模块维护。紧急凭证按已确认要求走无数据库、无任务校验的独立路径。
当前交接上下文允许修订或追加文字，暂不自动复制会话或建立执行流水。

### 生命周期

- 创建普通任务：待领取。
- 认领：待领取进入进行中；已进行中且租约失效的任务允许重新认领。
- 续期：由插件在后台检查并延长正式任务的本次认领，不向 AI 提供续期操作；temp 不续期。
- 主动释放：进行中回待领取，清除认领，保留任务内容。
- 标记阻塞：保存阻塞原因并释放认领；解除后回待领取。
- 完成：保存简要交接/结果，进入已完成并释放认领；验收细则另行讨论。
- 取消：用户本轮明确提供取消任务操作；保留“已取消”作为终态的建议。

租约失效只表示原认领不再有效，不推断任务完成、阻塞或失败。
过期的进行中任务显示为“认领已失效，可接管”，无需等后台定时清理才允许接管。
temp 创建时原子建立自身认领，默认有效期沿用已确认的 20 分钟。
temp 到期自动清空；正式任务 TTL、清理执行时机及运行中异步工作的收口稍后确定。

### 必须保证的约束

- 并发认领时至多一方成功；任务状态和认领字段在同一事务中变更。
- 新认领产生新的认领 ID，过期持有者的迟到续期/状态写入不能覆盖新认领。
- 正常操作的权限由当前认领及项目状态判断；错误消息说明失败原因。
- 删除项目后立即拒绝该项目任务的后续授权；记忆侧归档通过联动完成。
- 项目/任务 ID 与名称、数据库地址解耦。
- 以上能力及覆盖范围需通过实现测试验证；尚未开始编码。

### 模块

| 模块 | 首版职责 |
| --- | --- |
| types | 数据类型、状态及操作输入输出 |
| store | 连接配置、schema 迁移、查询与并发安全的写入 |
| service | 项目/任务业务操作、认领及权限检查 |
| DSH 接入 | tools 注册、调用者身份、hooks 和门禁 |

存储接口按实际业务需要定义，不提前做通用数据库框架。
后续讨论已采用 PostgreSQL 直连方向，见末尾数据库边界讨论。
对外工具和其他插件统一经任务服务调用，避免复制状态变化规则。

### 插件联动

- 提供项目、任务、会话有效认领及可访问项目的查询。
- 提供项目变化、任务变化及认领变化的提交后通知。
- 接收方在重启、重连及实际使用时可查询权威状态，通知只用于及时响应。
- 任务服务只返回项目 ID 等通用信息；记忆插件负责映射 Bank。
- 同项目持有两个任务时，释放一个不应使另一个仍授权的项目失效。
- 同步门禁粒度沿用上一轮待审建议；异步工作保存显式任务关联。
- 普通与紧急授权可供其他插件区分；紧急模式不派生项目 Bank 访问权限。

### 实现顺序建议

先审数据与状态约束，再逐批实现存储、任务服务，最后接 DSH 工具和联动。
本轮只保存设计，尚未创建上述源文件或数据库。

## AI 接口审查：2026-10-20 最新讨论

### 已确认能力与当前接口分组

1. 查看项目列表。
2. 查看任务列表。
3. 创建任务：参数选择正式、临时或紧急。
4. 查看任务详情。
5. 修改任务内容。
6. 任务状态变更：认领、释放、完成、阻塞、取消。
7. 创建项目。
8. 编辑项目说明。
9. 删除项目。
10. 查看项目详情。
11. 删除任务。

用户已补充项目创建、编辑和删除能力，其他插件可依赖任务模块提供的项目信息。
用户大体同意分组方案，补充 project_get 和 task_delete，形成项目五个、任务六个工具。
2026-10-23 已确认：task_delete 对正式任务软删除、对 temp 物理删除；已认领任务仅当前认领设备与会话可删除，过期认领等待回收。完整流转规则见 sagitta-task-storage.md。
项目和任务均支持编辑说明；任务具有标题和固定递增序号。

正式、临时合并在一个创建入口；紧急工作改由执行插件后续提供绿色通道，
无需任务 ID、不校验任务、不访问任务数据库。临时任务到期自动清空。备注维护并入修改内容的接口，具体参数待审。
任务内容可以包含文件等材料的引用。
状态变更由服务校验，失败时返回明确原因。

用户确认的自动能力：按设备和会话为正式任务认领续租，以及注入上下文。
temp 不续期。低频复查、执行流水继续暂缓；到期清理作为临时任务生命周期处理。

### 概念边界建议，尚未确认

- 项目：长期方向，保存范围和目标。
- 正式任务：决定推进的一项可验收交付；目标与验收说明其独立登记的理由。
- 执行步骤：正式任务内部的做法，写在任务上下文或链接文件中。
- 临时任务：有主题的短期工作上下文，普通 temp 仍沿用所属项目要求。

## 数据库与插件的部署边界：2026-10-21 待审建议

用户本轮要求先比较插件直连、插件维护数据库及封装独立数据库服务。
访问方式与结构维护是两个维度：插件可以直连独立数据库，同时维护该应用的建表/升级代码。

用户已选择直连：当前按独立运行 PostgreSQL、插件内部任务逻辑调用存储模块的方案设计。
本机或 VPS 只是数据库的部署位置；连接地址与凭据由插件配置提供。
数据库进程运行、备份和数据搬迁由部署环境管理。
插件仓库提供 schema 和版本迁移；安装/升级步骤执行迁移，运行时校验结构版本。
多设备版本兼容及迁移串行化需在实现时明确，避免多个客户端竞争修改结构。

| 方式 | 适用与成本 |
| --- | --- |
| 插件内嵌 SQLite | 本机部署简单；多设备共享和云端访问需另外设计 |
| 插件直连独立 PostgreSQL | 保持一个数据库服务，业务在插件内，适合当前最小范围 |
| 插件调用任务 HTTP 服务 | 业务规则集中于服务器，客户端可不感知表结构；增加服务部署、API、认证及版本维护 |

直连建议以本机可信客户端为前提；并发认领的互斥必须落实到数据库事务或条件写入。
它的代价是多个插件版本要与 schema 兼容；增加独立 Web/外部客户端后应重新评估 HTTP 服务。
未来迁出任务逻辑可以保留内部模块，但仍要补网络协议、调用身份、错误处理及通知机制。

任务逻辑与 DSH 接入分开：逻辑接收设备/会话等显式输入，存储只负责 SQL 及事务，
其他 Sagitta 插件调用任务模块公开能力，避免各自读写任务表。
直连已确认，具体结构和初始化流程待审，无部署或运行代码变更。
