# Sagitta 记忆插件讨论记录

更新日期：2026 年 10 月 20 日。

### 2026-10-20 补充确认

- `document_id` 由插件维护，同一会话在同一 Bank 复用稳定 ID；分段模型可读取少量前文辅助判断。跨 Bank 指代先按已讨论的简单方案处理。
- Theme 的 `meta` 指创建及管理属性，Agent 不直接修改正文。
- 用户倾向首版主动调用全部同步；后端异步操作的等待、超时与结果语义在适配时核对。
- 硬 refresh 以删除、修剪过时或矛盾信息为主，继续后置。
- 已授权准备 Manager 单仓库注册制的组织结构和空 memory 入口；真实记忆能力仍按功能逐块实现并由用户审查。

Sagitta 需要跨会话跟进长期工作、积累管理经验，并保持记忆后端可替换。当前使用本地 Hindsight 学习和验证记忆行为，正在讨论自建 DSH 插件 sagitta-memory 的使用规则。以下区分用户已确认要求、实现事实、建议与待确认问题，供后续逐步审查。

## 合作方式

1. 第一阶段：结合 Hindsight 官方集成和归档 memory 模块，由 Codex 逐项提问，用户决定期望行为。
2. 第二阶段：逐步编写代码，每一步由用户审查。
3. 讨论期间持续记录结论、设计理由、修正和待确认问题。
4. 当前仅开展需求讨论和记录。插件代码尚未开始编写。
5. 每个待决设计点先交代 Hindsight 官方的实际做法，区分服务 API 与官方 DSH 插件；再说明与 Sagitta 目标的适配情况、建议沿用或调整的理由及所需改动。用户明确优先参考符合 Sagitta 期望的官方实现思路。
6. 用户进一步明确：第一轮设计和第二轮逐步实现均以官方 API 为依据，重点讨论如何接入官方已有设计，以及如何接入 Sagitta 自身设计。实现时核对目标部署版本的公开 API／请求响应契约，文档与实际服务差异明确记录；官方插件作为调用示例参考。已有后端能力优先直接接入，Sagitta 的触发、任务权限、情境、分库协调和稳定工具接口通过清晰的适配边界实现。额外需求单列为 Sagitta 扩展，并在审查时说明实际调用映射和限制。
7. 用户最终澄清参照优先级：底层官方 API 最优先，决定可用能力、请求响应与约束；转接设计同时结合官方 Hindsight DSH 插件已有的工具封装、调用流程和默认策略经验，再依据 Sagitta 定位确定适配方案。讨论每个转接点时同时交代 API 如何支持、官方插件怎样使用、Sagitta 怎样接入及调整理由。此前 Codex 将纠正理解为“插件优先、API 仅作补充”属于过度修正，以本条为准。
8. 主 Agent 工具设计应形成一套统一、职责清楚的查询流程，减少不必要的选择。底层 API 的多种能力可以由插件协调使用，不能据此直接把所有后端操作平铺成主 Agent 工具。新工具需先说明现有流程的缺口及独立入口的必要性。
9. 用户要求按完整功能点讨论取舍，交代依赖的接口和副作用；既不一次推完所有设计，也不把一个完整功能拆成多个琐碎决策。硬 refresh 等长期维护记录到 roadmap 后续再议。第一阶段讨论与第二阶段逐步实现的安排保持。

## 最新功能取舍 2026 年 10 月 19 日

本节为用户最新功能定义，覆盖下文历史提议中的冲突项。仍处于设计阶段，工具具体契约与后端映射将在实现前逐步审查。[后续路线图](sagitta-memory-roadmap.md)记录延后能力。

### 访问范围与命名

- Sagitta 持有有效 project_id 与 base_id；base_id 索引常驻基础 Bank，有效项目对应的 Bank 激活。项目／任务激活由另一插件决定，记忆插件挂载触发点并校验有效访问范围。
- 主动查询仅访问 bank_id 指定的单个库，基础库由 AI 按需另查。用户已明确选择这一项，撤回同一请求默认向所有激活 Bank 查询并拼接的表述。
- Sagitta 将主题总结称为 theme，内部适配为 Hindsight Knowledge Page；目录作为文件夹组织 theme。
- 既有默认库权限、temp 归属项目和项目归档后对 AI 不可见／不可恢复等约束继续生效。

### 上下文注入

- B1 确定采用：注入 Sagitta 自己的工具使用说明，具体内容与提醒频率后续确定。
- B2 确定采用：会话开始注入基础库相关信息，任务领取／激活时注入项目和任务情报。自动 reflect 用 low，主动 reflect 默认 high；可选 depth 保留。失败处理参考官方。

### 自动处理与运行维护

- C1 确定采用 AI 一轮结束时的自动记录。多 Bank 场景由后台 AI 将新增对话分为尽可能少的片段并指定目标 Bank。用户最终明确：分段 AI 可以读取少量前文作为归属与指代判断背景。该背景用于路由，分发处理对象仍为新增内容；历史上下文是否需要重复写入、如何引用补充，不能与背景读取混同。
- 用户先提出每段附总结，随后提出只分段并利用 Bank 的增量处理；是否附段摘要尚待定。原文作为输入保留，摘要不得未经确认取代原文。
- 用户提出将同一 Bank 的片段按原序拼接，省略其他 Bank 内容的位置用省略标记，并在说明中告知原因。该方向待验证：标记只能说明缺口，不能补回被省略内容中的实体、指代与因果关系；跨项目依赖需要明确补充规则。
- 一库场景是否完全跳过分段 AI、基础库选择性提取的具体实现仍待细化。此前基础库避免灌入所有项目对话的要求继续保留。
- 官方 append 需要同一 Bank 内稳定 document_id 才能累积同一条材料流。每段另建独立文档不会自动拼回对话。会话到分库文档 ID 与增量游标的映射属于后续实现契约。
- C2／C3 当前不照搬官方 Git 自动导入或后台代码调查。未来独立 analysis 能力可接成熟方案，由 Agent 主动将所需结果上传记忆库；不默认把整套分析流程放进 memory。
- C4 确定需要：创建项目时预建 theme；预设内容后续设计。
- C5 为已有 theme 的正常 auto-update。用户倾向按调用次数及时间条件触发，可配置；“调用”计数对象、AND／OR、最小间隔／最长延迟尚待明确。
- 用户重新明确 refresh 语义：硬 refresh 应清理过时／矛盾信息，使当前有效知识保持更新。它超出 Hindsight 页面 full refresh，作为独立长期维护能力延后设计。历史事件的保存、当前事实的失效、更正后的证据和无法判定的冲突需区分，不能保证单次维护得出全部真实最新信息。
- D1：插件启用时自动挂载记忆能力；本地服务启动或远程连接等具体方式后续确定。
- D2：自行编写 Sagitta 工具说明，配套独立 skill 的必要性另议。
- D3：插件更新统一由 sagitta-manager 管理。
- D4：保留必要运行记录。

### 官方能力核对与建议 待用户确认

- 官方支持 operations 列表和单操作状态查询；异步 retain、theme 首次生成等可返回 operation_id。无需为 Hindsight 本身重建任务队列，但本地分段／分库作业进度不自动包含在服务的 operation_id 中。
- 建议查询与目录操作正常同步返回；上传提取与 theme 生成采用异步并返回操作引用。同步 retain 完成不代表后续 Observation 与所有 theme 已更新，状态应区分各阶段。此为建议，尚未决定统一等待策略。
- 官方节点 PATCH 支持标题、父目录、source_query、范围与预算等；修改 source_query 会排队重建正文。普通页面管理接口没有直接正文字段；若要编辑正文，需要另外核对 mental-model 能力与自动更新语义。
- 官方支持对原始事实更正和失效处理；Observation 从来源重算。页面 full refresh 不清理底层错误事实。原文重处理可能重建之前已失效的事实，硬 refresh 需后续设计证据与再处理策略。

## 当前自动记忆规则摘要 以本节最新确认为准

- 自动记录沿用 AI 一轮结束后的后台分流与写入流程。
- 新会话自动召回一次基础 Bank；每次任务激活时自动召回其所属项目 Bank，temp 的项目背景召回沿用既定规则。
- 用户最新确认：上述自动注入调用 reflect，仿照官方编写 Sagitta 专用提示词，重点强调 Sagitta 的管理型伙伴定位及需要自动提醒的内容；主动 recall／reflect 继续提供。提示词正文尚待逐项讨论，未修改运行配置。
- 自动 reflect 的情境输入已获确认：新会话使用首条实际输入并附已有生效任务的现有目标／进度；任务激活使用目标任务及项目的信息，字段存在时提供进度与本次行动。直接读取既有数据，输入不足时保留不确定性。
- 用户要求区分主 Agent 可见的简洁字段与 Hindsight 适配层的完整后端参数；逐项确定稳定工具接口和后台映射。
- 主动接口以文首最新功能清单为准：用户重新提出 memory_recall 与 theme 文件树操作，查询只访问指定 Bank；具体后端映射待审查。
- 主动查询默认返回简洁结果与来源引用，原文按需读取；适配层使用官方来源返回能力，具体来源读取工具及字段后续讨论。
- 用户补充：会话内每隔若干轮自动召回可在后续做成配置项；当前暂缓设计，未确定间隔或默认启用。
- 用户已撤回逐轮自动召回方案；同一任务持续推进期间的信息需求交由 Agent 主动 recall／reflect。
- 召回结果按简单写入会话历史的方向设计，输出总长度上限仍需确定。
- 向 Agent 提供主动 recall／reflect 工具及持续可感知的使用说明。主动查询的触发习惯尚需提示设计和后续测试。
- 自动 reflect 使用 low，主动 reflect 默认 high，保留可选 depth；失败处理参考官方。更早的按输入类型决定逐轮预算方案作为历史保留。

## 目标与边界

- 用户最新明确的三项设计目标：尽量借鉴 Hindsight 官方插件的工作流；结合超长期经验成长、多个动态激活 Bank 及任务认领联动做必要适配；主 Agent 使用的工具与语义保持后端无关、稳定。theme 通用管理已确认；硬 refresh 等事实维护能力先作为后续需求保留。
- 首要目标是长线、多任务、少人工介入的工作，以及跨会话经验积累；人格与主体性的进一步发展后置。
- 保留 DSH，制作适合管理型 Agent 的记忆集成。Hindsight 作为初始后端接受黑箱验证。
- 记忆接口和实际后端行为需要解耦，为未来更换模型或记忆后端保留空间。
- 经验效果评分需要先有改善效果的证据，不默认引入评分机制。
- 用户审查系统程序和提示词的修改；Agent 可以使用已提供的系统能力，并反馈机制问题。

## Hindsight 已核对的使用事实

这些是本地 Hindsight 1.0.0 的实现事实，不自动成为 Sagitta 的接口设计。

| 对象或操作 | 含义 |
| --- | --- |
| Bank | 数据与处理配置的归属范围。跨 Bank 的查询组合由调用方组织。 |
| Document | 提交的原始材料；开启原文保留时，正文保存于数据库。 |
| Memory Unit | 提取事实和 Observation 共同使用的存储对象，现有类型为 world、experience、observation。 |
| Observation | 依据待整理事实、相关旧认识和部分来源事实，由 LLM 生成或更新的认识。 |
| 实体和图谱 | 实体、实体与记忆的关联、记忆之间的连接及共现数据，帮助查找相关记忆。 |
| Mental Model | 某个主题的正文、整理问题、来源和刷新配置等。 |
| Knowledge Page | 一条页面记录关联一个 Mental Model；Knowledge Base 另有文件夹节点，用于组织多篇页面。 |
| retain | 提交材料，提取事实并保存检索信息；自动整理开启时继续处理 Observation。 |
| recall | 查询记忆条目，可附带实体、原文片段和来源事实等；普通响应不直接包含 Mental Model 正文。 |
| reflect | 使用 LLM 检索、分析记忆，并按配置参考 Mental Model，形成回答。 |

事实提取、Observation 整理、reflect 和主题文档刷新使用生成式 LLM。普通召回主要使用检索、embedding 和可选 reranker。官方提供内置提示词，可通过 mission、附加指令、材料范围和预算等配置调整行为。

### 主题文档维护边界

- 创建知识页面会创建配套 Mental Model，并异步生成第一版正文。
- 页面主题／结构需要通过创建接口显式建立；创建的调用者可为用户、插件初始化逻辑或 Agent 工具。官方 DSH 集成可初始化预设页面，并提供 capture_initiative 记录新事项及关联页面。页面建立后，Hindsight 根据 source_query 和范围配置自动生成／刷新正文。当前官方页面默认使用 Observation、增量刷新及整理完成后触发；可改为定时刷新。普通 retain 自动提取／整理记忆与自动决定新增知识页面主题是两个不同能力，本次核对未将后者认定为默认行为。
- delta 模式参考旧正文和新增或变化的材料，进行局部修改；full 模式正常生成时从当前允许的材料重新检索组织正文，排除当前页面自身。
- full 刷新在没有可读来源或发生异常时可能保留旧正文，因此删除全部来源不等于正文必然自动清空。
- 页面可以在整理后或按定时规则检查刷新，支持最小自动刷新间隔。当前页面触发配置没有直接的“累计 N 条未读记忆”阈值。
- 修改、删除和失效记忆有后续整理及来源撤回处理；修改页面范围、失败暂停等情况仍需要显式维护。
- 自动处理进度追平，不能证明 LLM 生成的正文在语义上完整准确。Hindsight 没有提供任意合法操作后都自动达到有限语义差异的一致性保证。
- 人工修改提取事实不会同步修改原始 Document；重处理原文可能再次提取旧表述。

## Bank 规则

### 当前结构 已确认

用户确认将两个常驻库合成一个，项目 Bank 仍各自保留。常驻库中可预先建立不同主题文档；日常内容、工作经验、用户和自身认知等具体主题划分继续讨论。

此次合并简化常驻材料的归属。此后用户已确认由后台协调模型选择原文片段及目标 Bank，再由 Hindsight 分库提取处理，详见“基础库与项目库采用不同分发规则”和“分发流程与官方触发时点对齐”。项目访问和删除要求继续生效。

### 两类 Bank

当前只开放常驻 Bank 和与任务联动的项目 Bank。自定义、非项目 Bank 的创建能力和设计暂缓。

| 类型 | 读写和注入 | 生命周期管理 |
| --- | --- | --- |
| 常驻 Bank | 一个常驻库，日常聊天也可随时读写，参与默认召回。 | 由系统维护，Agent 没有直接创建、改名、删除入口。 |
| 项目 Bank | 正式任务授权或本轮提出的临时任务机制决定访问与召回；具体联动边界继续确认。 | 跟随长期项目，由任务系统发起相应生命周期操作。Agent 通过项目管理操作影响它。 |

此前两个常驻库承担的工作能力、管理经验、工作交接及用户、自身、世界认知，合并在同一个 Bank 内。具体名称、内部主题和注入预算继续细化。

### 归属与查询

- Agent 根据系统提供的可写 Bank 清单，决定一份新材料写入哪个 Bank。
- 调用记忆写入接口时通过参数显式指定 Bank。该原则已确认；异步流程中由哪个 Agent 执行这次调用正在进一步明确。
- 系统将可写 Bank 的说明注入上下文，使 Agent 知道如何选择。
- 项目记忆的访问范围与自动召回跟任务机制联动。日常默认库不需要先认领任务。
- 正式任务和 temp 均必须归属某个项目，记忆模块通过所属项目定位项目 Bank。
- 其他项目可先通过任务查询发现。仅为轻量侦查而开始正式执行认领，不符合用户期望。
- ambiguous_bank 是用户早先提出的候选方案。当前讨论以轻量临时任务处理该场景，未确定保留 ambiguous_bank 入口。
- 是否同时向多个 Bank 写入、怎样把项目经历提炼到通用经验库，尚未拍板。

### 项目删除

- 项目 Bank 在存储侧归档保留。
- 项目及其 Bank 对 Agent 表现为硬删除：不可见、不可访问、不可恢复。
- 不为 Agent 提供归档查询或恢复入口。
- 归档后的后台整理与文档刷新如何停止，以及已有排队操作如何收口，留待确认。

## 轻量临时任务 用户提出的规则

用户希望沿用旧 temp 的轻量性，让 Agent 可以进行侦查、记忆访问和顺手执行脚本等轻量工作。temp 由各 Agent 创建自己的任务，不是认领或独占另一条已有任务。

1. Agent 创建自己的轻量 temp，和正式任务一样必须挂在某个项目下；通过所属项目定位对应 Bank。
2. 创建 temp 后触发对应记忆的自动召回，使 Agent 获得背景后再提交材料。
3. token 默认在 20 分钟后自动归还。
4. 申请时可以选择更长时间，也可以续期。
5. 主动查询能力继续保留；临时任务中的自动召回是获得背景的兜底。
6. 沿用旧 temp 的执行能力，包括修改文件、运行命令、委派子 Agent 等执行操作；本轮不重新设计任务授权系统。
7. 任务级文件操作隔离留待以后讨论。当前将任务系统视为黑箱，记忆模块只需明确授权、项目关联、有效期和生命周期变化等输入。

“token”暂按用户原词记录。它的具体权限范围、是否需要实际凭证、到期后的处理方式，尚未定稿。

### 待确认的临时任务边界

- 到期或主动归还之后，停止哪些自动注入与后续操作？已经提交的后台写入如何处理？

这里只继续询问影响记忆行为的边界。任务记录清理、正式任务认领和文件隔离等留给任务系统设计。

## 自动记录与主动附件

用户倾向于日常记忆采用异步自动收集，由异步模型识别值得保存的内容，包括主 Agent 表达的记录意图；主 Agent 额外提供主动上传附件的入口。通用的主动文字补记工具暂不作为必备能力定案。

Bank 通过调用参数明确指定，避免把这一点重新当成未决定的分库策略。待确认的是异步收集流程的调用主体：后台记忆 Agent 是否自行选择并带入 Bank，还是主 Agent 指定本轮 Bank 后由后台处理材料。

具体记录哪些消息和工具结果、提交时机、附件输入与解析方式、失败处理，随后分别询问。附件上传作为增加材料来源的能力，需要明确目标 Bank，并沿用已有的任务访问范围。

Hindsight 自带的事实提取在调用方已指定 Bank 后进行。如果要求后台模型根据多个可写 Bank 自主选择目标，需要在 Sagitta 收集流程中明确这一职责；不能直接假定 Hindsight 的库内提取器已经提供跨库路由。

### 早期后台分流建议 历史方案

用户已确认常驻库合一、项目库各自保留。该早期建议一度暂缓，此后经讨论，用户已确认后文的后台片段选择和分库写入流程。以下保留早期方案的理由与差异，当前结论以后文已确认方案为准。

官方 DSH 插件默认给一个仓库会话绑定一个 Bank；Hindsight 服务的写入边界则是一次请求指定一个 Bank。同一段会话的不同材料可以由调用方分别提交到不同 Bank。

Codex 建议由 Sagitta 的后台收集模型进行分流，主 Agent 保留附件上传时显式指定 Bank 的能力：

1. 保存会话原始增量、来源、任务与项目上下文，供处理失败后重试及追溯。
2. 后台收集模型读取材料、可写 Bank 清单及职责说明，输出目标 Bank 和对应原文片段。
3. 程序检查写入范围，并将各份材料分别提交给 Hindsight。
4. Hindsight 使用自身的事实提取、Observation 整理和主题文档刷新机制。

分流模型先负责归属和片段选择，尽量保留原文与必要上下文。经验概括和既有记忆整理仍交给 Hindsight，避免两层模型重复改写。项目归属清楚的工作材料利用任务信息定位；对话中明确适用于所有工作的要求可分到常驻工作库。

该建议增加一轮后台模型调用及分流错误的可能，需要保留原文、目标库和分流记录，以便检查和重新提交。归属不清的材料如何处置，以及授权到期时已排队材料的处理方式，另行确认。此建议尚未成为实现决定。

### 会话上下文的连续性 待确认

用户指出按 Bank 直接截取句子可能失去上下文，尤其是指代、同意、限制条件和后续纠正。前面的按句分库示例只表达归属，不足以作为实际提交规则。

Codex 建议区分完整会话底稿与 Bank 内的入库材料：

- 完整会话按时间、消息标识和说话者保留，优先复用 DSH 已有会话记录；具体持久化、备份与留存方式后续确认。
- 后台收集模型读取连续对话及任务上下文，必要时向前回读，以连贯问答或主题段落为提交单位，保留必要前文。
- 各 Bank 中的 Document 保存实际提交的连贯材料，同时携带可追溯到完整会话的来源信息。原始会话底稿不会被分流操作拆散或覆盖。
- Hindsight 只直接处理调用方提交的正文和上下文。外部会话引用用于 Sagitta 侧追溯，不能假定 Hindsight 会自动沿引用读取 DSH 日志。
- 原文保留提供追溯与重处理基础，无法单独保证每次材料选择都包含全部必要语境。黑箱测试应覆盖省略指代、同意范围、多轮纠正和跨话题回指。

此方案及材料切分粒度尚待用户确认。

### 任务上下文与话题归属

Codex 建议优先从任务系统取得当前有效任务、所属项目和访问范围；对话中的实际话题可能变化，不能由有效任务集合完全推断。正在询问是否可以要求任务黑箱提供主 Agent 明确选择的“本轮当前任务／项目”，区别于一组已认领任务。该输入及混合话题的处理规则尚未定稿。

### 项目库写入路由的针对性复查 2026-10-17

核心问题：一段持续、混合话题的对话中，由谁、依据哪些信息，将材料写入哪个项目 Bank；同时保持任务访问范围与必要语境。此问题独立于写入后的事实提取和 Observation 整理。

复查发现：

- MemOS 开源 HTTP 写入路径的 AddHandler 接收 writable_cube_ids，构造 CompositeCubeView。后者对所有指定 Cube 分别调用 add_memories，源码注释明确目前为 fan-out、未来可增加智能路由。因此这个多库参数不能被理解为“从允许的库里自动选择”。这是所查路径的事实，不外推到其他版本或商业后端。
- memwal-sharing 有公开写入路由实现：先按内容关键词识别偏好、决策、Bug、约定等类别，再按配置映射至用户库、共享库或当前 Git 项目库。项目身份来自当前仓库；它没有根据混合对话语义在多个项目之间挑选的机制。项目规模很小，仅作为可读实现对照，不作为成熟度或效果证据。
- Anona 官方 SDK 明确暴露 route="auto"，文档描述根据各 Space 声明用途选库，并返回 rule/model/fallback 阶段、原因及目标库；当前一次写入至多选一个库，批量记录整体作为一个路由单位。公开仓库是托管服务 SDK，尚未核实服务端分类算法、连续对话关联策略和准确率，不能称作可直接复用的成熟开源路由器。
- Hindsight、Graphiti、LangMem 前次核对的接口由调用方指定 Bank、group_id 或 namespace。它们的库内语义归并不能证明具备跨项目自动写入路由。

截至本次针对性复查，尚未找到经过充分验证、可直接复用、能够自动将混合对话准确分配到 Sagitta 各项目 Bank 的成熟开源实现。此为检索结果的边界，不是证明此类实现不存在。后台模型选库仍属于需要单独设计和验证的 Sagitta 集成工作。未新增接口或实现决定。

### 隔离与自动分库的复杂度取舍 待讨论

用户表示不希望承担混合会话分库的复杂度，同时认为隔离似乎仍有必要。这是当前顾虑，并非对新增方案的确认。

Codex 提出一个可验证的简化取舍：保留现有 Bank 边界，自动写入先覆盖归属明确的材料，例如携带项目标识的任务执行记录、主动上传时已选定 Bank 的附件。对于归属不明的混合对话，保留原始会话，暂缓自动入库，并允许后续带明确目标补录；具体补录接口仍待讨论。常驻库同样只接收归属已明确的材料，避免将整段含项目内容的主会话默认写入常驻库而绕过项目边界。

代价是部分混合对话内容可能未自动形成可召回记忆。原文留存提供补录条件，不等于原文已经纳入长期记忆检索。此方案改变自动收集覆盖范围，尚未获得用户确认；Bank 数量、任务访问和项目删除规则继续沿用。

### 同一材料多库提交、各库按职责提取 用户新提议待评估

用户提出：同一段材料同时交给多个库，各库的 AI 只提取与自身有关的资料。这里暂按“各 Bank 的后台提取模型”理解，属于候选方案，尚未确认实现。

Hindsight 当前官方文档明确支持每 Bank 的 retain_mission，将该库应关注的范围注入提取提示词，可复用服务自身的提取过程；同一模型也能在不同调用中承担不同 Bank 的提取工作。Sagitta 仍需组织多次、各自指定 Bank 的写入请求，并遵守既有可写范围。该方案把跨库选择变成每库分别判断相关性，减少独立路由步骤，同时让各次提取看到连续材料。

关键限制：

- mission 属于 LLM 提取指引，不能保证全部提取正确或完全排除无关内容。需要验证误入、漏记、边界与跨项目比较场景。
- 输入材料会按接收 Bank 数重复处理，提取输入成本随之增长；无需为每 Bank 常驻独立模型。
- Hindsight 默认保存原始 Document 与 chunks。mission 缩窄事实范围，不会同步裁剪已保存的原文；Document API 和 recall 的 include.chunks 可以返回原始材料。即使只正确提取 A，A 库中的来源仍可能包含 B。下轮核对发现可按 Bank 关闭原文保存，具体修正见后文。

- 官方仍提供 `hindsight_ingest_document`，用于主动保存外部资料、笔记、研究发现和更正说明；另有 `hindsight_capture_initiative`，记录计划并建立或关联知识页面。
- 普通对话已有自动回写时，Agent 无需重复调用保存工具。保留主动写入可用于明确材料、特定目标库或工具结果中的重要发现，其具体必要性取决于 Sagitta 的自动记录与分库规则。
- 官方的主动材料写入绑定已解析的 Bank。Sagitta 要求的 Agent 显式选库，需要我们定义自己的接口或路由规则。

### 2026-10-19 主动工具完整审查与讨论节奏修正

用户明确要求按完整功能流程讨论，兼顾收敛速度与依赖关系；“加快”不意味着一次完成所有设计，“放慢”也不意味着拆开每个字段逐一确认。提出接口前需交代它依赖的其他入口，避免将候选方案当成已定接口。当前 memory_list／memory_search／memory_read 仍属提议，未获得整套确认；refresh 留待后续。

本次重新读取固定提交 6843203b7cd2c2ee300880ca6ab1530829598662 的 dsh.ts、knowledge-tools.ts、hindsight.ts、status.ts、runtime.ts。官方 DSH 原生主动工具共八个：sync_status、diagnose、search_knowledge_pages(query)、list_knowledge_pages()、read_knowledge_page(page_id)、reflect(query)、capture_initiative(title, summary, relates_to_page_id?)、ingest_document(title, content)，均带 hindsight_ 前缀。调用时由工作目录／配置解析 Bank；AI 工具参数不包含 bank。

官方访问映射（路径均以 /v1/default/banks/{bank_id} 开始）：list 读取 GET /knowledge-base/tree 并展开页面叶节点；search 调用 GET /knowledge-base/search?q=…&limit=…；read 调用 GET /knowledge-base/pages/{page_id}，正文仅返回一次；reflect 调用 POST /reflect，预算来自配置、默认 high，工具只交回 text。页面 ID 为知识库页面节点 ID，与内部 mental model ID 区别；list/search 返回的 ID 可直接用于 read。

capture_initiative 新建时查找或创建 Initiatives 文件夹、POST /knowledge-base/pages 创建主题页面，再 POST /memories 异步写入计划材料；关联既有 page_id 时复用页面并异步写入更新材料。新建与最近一次更新材料分别有稳定 document_id。工具返回 page_id，正文生成仍需后台流程。ingest_document 接收文字 content，由标题生成稳定文档 ID，添加来源标签／元数据，POST /memories 且 async=true，返回 ok 与 doc_id；它本身不读取文件路径、不负责 PDF/OCR。工具描述还建议写入更正说明，但此建议不构成旧事实物理删除或全局一致性的保证。

sync_status 组合文档目录、页面树、后台 operations 与本地 Git 信息；diagnose 读取本地配置／运行时信息并隐藏密钥。官方主动工具未包含独立 recall、原文读取、任意页面 CRUD、手动 refresh 或 Bank 管理。上述为审查事实，尚未决定 Sagitta 全量照搬哪些工具。

### 2026-10-19 自动 Hook 与自动处理复核

用户随后纠正讨论方式：须以可独立选择的功能点编制清单，由用户逐项决定是否采用和如何采用；工具指引注入、首次 reflect 注入、主动查询返回、每轮结束自动记录等分别列项。事件与调用链只是每项的实现说明，不能替代功能清单。此前将 refresh 记为页面正文更新的理解已被用户纠正：正常页面更新称 auto-update，refresh 指清理过时／矛盾信息的硬维护。用户本轮确认自动 reflect 使用 low、主动 reflect 默认 high；失败处理可参考官方。先前允许主动调用可选 depth 的决定保留。代码仓库自动调查应作为未来独立代码分析能力考虑；本轮未授权实现。

按用户提出的三个观察面解释插件：AI 主动工具、上下文注入、条件触发的自动操作；注入属于 Hook 的一种输出。核对同一固定提交的 dsh.ts／runtime.ts／hook.ts／knowledge-injection.ts／config.ts／session-start.ts：DSH 注册 session-start、pre-step、turn-stopping、disposed 四个事件。session-start 发起工作区初始化；pre-step 仅对新真实用户输入执行 onPrompt，纯工具续跑跳过；turn-stopping 读取完成后的对话并启动后台增量 retain；disposed 清理 DSH 活跃 Agent 和注入去重记录。

默认 autoInject=reflect，在首次有效用户输入前以提示模板加输入调用 low-budget reflect，默认超时 20 秒，成功正文注入一次。新库可延后首次尝试；失败有有限重试，符合条件的超时或服务错误可降级为页面搜索、再 recall。注入作为 plugin:hindsight 来源消息进入会话历史，相同完整块避免连续重复追加。

纠正此前“周期注入页面目录”的宽泛说法：knowledge-injection.ts 的实际 indexLine 只输出页面数量和搜索／阅读指引，不输出页面标题和 ID。内部仍拉取并缓存目录；pageRefreshEveryTurns 默认 1，周期生成工具指引，DSH 再对完整注入块去重。源码顶部仍有每轮注入页面片段的旧注释，实际 buildHookOutput 已明确移除该分支，正文由主动工具获取。首轮还有初始说明。目录提示刷新与知识页面正文重新生成是不同操作。

后台初始化按配置可进行 Git 导入、预设页面建立、无界面编码 Agent 的代码调查；已有仓库达到提交数量阈值等条件可再调查。运行时还按配置处理本地 daemon、配套 skill 同步和插件自动更新。页面定时更新由服务端执行：此插件创建页面默认配置错峰每小时 cron，亦可配 auto-refresh 或 manual；该默认不能与服务直接创建页面的默认混用。事实提取、Observation 整理及页面生成使用服务配置的 LLM。

工程判断：工具与上下文拼接逻辑直接，长期运行的实际难点是增量写入游标、串行与重试、动态 Bank 授权和已确认的异步分库。官方以真实用户输入为 pre-step 触发门槛，Sagitta 的任务激活／自主推进触发需要自行衔接。上述为实现审查和差异说明，未新增接口或配置决定。

对官方 capture_initiative 的解释收敛：AI 使用层面可理解为将创建与更新计划页面合在一个工具里。不传 relates_to_page_id 时建立页面并提交初始材料；传入时复用已有页面并提交变更材料。提供初始材料可作为创建动作的一部分理解，无需让用户额外理解成一种独立操作。工程上，更新分支调用 retain 写入关联材料，供后台维护正文，并未直接 PATCH 页面标题、目录位置、整理问题或正文；不能据此认为它提供通用页面编辑。

### C1 增量写入与提取上下文核对

用户以“先说 a、后说 a 不好改 b”询问前文是否丢失。固定提交的 chat.ts／retain-cursor.ts：同一会话使用稳定 conversation:{sessionId} 文档 ID，初次／不确定状态提交完整规范化会话；确认支持 append 且前缀一致时，仅传新增 turns，并设置 update_mode=append。服务 orchestrator.py 先读取旧文档正文并与新增内容拼接，然后分块；PostgreSQL delta 路径跳过未变块，_build_delta_contents 仅把需要处理的块及共享 context 等元数据送入提取流程。故网络上只传增量不等于服务丢掉前文，但文档保存全历史也不等于每次提取模型看到全历史。短会话若仍处于同一块，可以一并看到 a 与改 b；跨块或远距离指代仍需实测，不能承诺自动恢复全部上下文。官方 chat-log 指南同样强调同一会话稳定 document_id 和 append／replace，避免逐句独立 retain。本轮未改设计或代码。

复核官方 Knowledge Pages API：显式指定 name、source_query 创建页面后，后台生成正文，并按配置更新；文件夹通过显式创建与 parent_id 组织。已核对的官方服务／DSH 插件实现未提供根据全部记忆自动发现新主题、生成分类目录的通用机制。插件自动建立的预设页面及 Initiatives 文件夹来自程序规则；capture_initiative 由主 AI 主动调用后创建页面。自动 Observation 整理与自动建立 Theme 是不同能力。若需后台自主发现 Theme 和组织目录，需要另加调用策略；当前仅说明边界，未决定新增实现。
