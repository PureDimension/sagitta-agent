# 异步执行接入讨论

日期：2026-10-26。状态：源码核对与方案讨论，尚未实现。

## 已确认方向

- 异步执行由调用方提供 claimId，校验有效后放行；复用当前设备与会话身份。
- 后续记忆模块消费执行关联信息，考虑开始/结束快照、过程记录和工作目录联动；本轮不实现这些能力。
- 原有绿色通道约定保留，具体工具参数及与异步派发的组合仍需确认。

## 固定版本事实

核对当前安装的 DSH 0.2.1-rc.2，以及 npm 发布的同版本 dsh-subagent-codex 包（只读取包内容，未安装）。

- 官方工具经 ctx.subagents.startActivation 启动，接受后返回 childId，DSH 管理执行和完成通知。两种后端均已支持这种异步调用。
- spawn/fork 是 DSH 本地可续行子会话：spawn 使用独立对话，fork 继承父会话已完成轮次，不包含正在执行的当前轮次。spawn 可选择独立预设；fork 继承父预设。
- sendMessage 对运行中子会话在步骤边界投递，对空闲子会话开启新轮次，也支持从持久化恢复可续行子会话。此能力不等于重启后恢复正在执行的外部进程。
- Codex 后端每次启动一个 app-server，创建 ephemeral thread 并运行一个 turn；不支持追加消息、续聊、进程池或产品会话恢复。one-shot 指一次完整 Agent 轮次，期间可以多次调用工具。
- Codex 使用自身配置、认证和工具；不接受 DSH agentPreset/agentOptions/outputSchema/depthLimit。包依赖固定 Codex 0.153.4，当前未在本机安装或运行该后端。
- Codex 对 DSH 暴露最终选定回答/停止原因及安全诊断，不提供逐步工具活动流。父会话保存外部执行身份和终态结果，没有本地子 Session。
- DSH 提供 subagent/start 和 subagent/end 观察事件，包含 runId/childId/provider 等；start 已在子执行发布后，不能承担执行前授权或严格的执行前快照。
- tools.guard 是同步检查，不能直接 await PostgreSQL。当前官方子 Agent 工具参数不含 claimId。

## 与归档的差异

- archive/legacy-2026-10-15/plugins/codex-dispatch 使用常驻 app-server，提供 dispatch/status/append；与官方一次性后端的能力不同。旧 append 实现不作为新版协议正确性的证明。
- 旧 async-work 自建进程内运行登记和最近终态缓存，没有跨进程恢复。
- 旧 memory/task-gate 用缓存及任务 ID 判断授权；部分工具只要求存在任意认领。新方案要求显式 claimId 精确关联执行，不能原样复制旧门禁。

## 建议，待确认

- 保留 DSH 执行运行时；Sagitta 接入层负责明确的任务授权和执行关联。
- 任务插件提供按 claimId、设备、会话校验的公共能力，返回 taskId/projectId 等关联；当前仅有展示认领和任务内部校验，尚未发布此服务。
- claimId 表示一轮认领，childId 表示执行者，runId 表示执行轮次；记忆后续需要保留稳定 taskId/projectId，避免认领清除后丢失归属。
- 初始派发校验不等同于持续授权；运行中租约失效的策略、追加消息校验、取消权限和 Workflow 内派发如何受控需要单独确定。
- 若接受 Codex 一次性执行，可直接复用官方后端；若首版即要求续聊或详细过程记录，需要扩展后端，工作量显著不同。

参考：官方 [Codex 后端说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/subagent/subagent-codex/README.md)；实际结论同时核对 npm 0.2.1-rc.2 包内 README 与 lib/index.js。本机原生后端及类型来自对应版本 dsh-subagent、dsh-tool-subagent、dsh-subagent-spawn-in-process、dsh-subagent-fork-in-process 和 dsh-tool-subagent-control。

## 推进顺序建议（2026-10-26，待审查）

用户提出任务认领后周期性由辅助 AI 检查偏离、停滞、重组必要性及持续进展，向主会话注入提醒；候选周期为 30 分钟或 1 小时。异步执行需关联 claimId，未来记忆消费任务快照和操作历史。

建议顺序：最小执行证据与关联 → 异步委派接入 → AI 复查与自主推进 → 长期记忆整理与召回。

- 第一阶段定义任务/认领/会话/执行之间的关联，记录任务开始时的目标、约束和可用完成条件，引用原生日志。当前快照建议先指任务与执行状态；文件内容快照的范围另行确认。原始要求和后续明确变更应可追溯，避免只用最新总结作为纠偏基准。
- 第二阶段补齐任务对外 claim 校验，派发前绑定，关联启动、结束、失败与结果。复用 DSH 原生执行和事件。Codex 续聊与细粒度过程采集仍需单独决定。
- 第三阶段通过公共调度组件注册复查，建议按主会话合并检查其已认领任务，避免每个任务重复唤醒同一主 Agent。读取起始依据、当前状态、上次复查以来的证据；支持证据不足结论。复查结果为建议，运行时重新检查任务有效状态；用户授权范围外的新方向仍由用户决定。
- 周期复查可作为首版入口；子执行结束后的及时处理也需要保留，长线推进不应全部等待定时器。执行停止或宿主关机时的恢复另行设计，不将用户离开等同于宿主关闭后继续运行。
- 第四阶段将结果、纠偏建议及后续效果作为记忆来源，再接经验召回。先证明可以发现并改善具体工作问题，辅助 AI 数量增加的收益仍待真实任务验证。
- 全部操作记录属于执行观察范围，既包括同步工具也包括异步子任务。同步操作若没有显式任务关联，应先保留会话归属；多任务下无法仅凭当前认领列表可靠推断唯一任务，绑定方式待确认。

## 校验包装与日志范围（2026-10-26，待审查）

- 用户提出监督模型与 Sagitta 双向通信，并希望使用类似注解的公共包装，统一校验 claim、放行、记录工具输入输出。本轮只讨论记录范围。
- 固定版 DSH 提供异步 tools/pre-execute、环绕 tools/execute 和最终观察 tools/result；之前确认同步的是 tools.guard，不能将这个限制推广到整个钩子系统。
- 建议受控能力通过统一注册/包装接入，工具定义声明所需 claim 参数；任务公共服务校验，执行观察记录关联。DSH 已有 tool/call、tool/result 和用户/助手消息事件，可引用原始会话日志，避免每次工具调用复制全部上下文。
- 建议操作记录保留 taskId/projectId/claimId、会话及调用 ID、时间与结果关联，按需从会话读取附近消息。完整模型请求包含动态提示词、工具定义及历史选择，不等同于会话消息；首版不默认保存每次完整请求快照。
- 包装器只能观察调用边界。异步派发返回 childId 表示已接受，最终结果需要执行结束事件；子 Agent 内部操作须监听对应子会话或后端事件。官方 Codex 后端缺少详细过程流的限制仍适用。
- 原始会话日志引用依赖其保留及可访问性；未来长期存档应在清理源日志前保存需要的证据。此方案尚未决定新的存储表或实现函数。
