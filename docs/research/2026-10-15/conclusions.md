# Sagitta 长期成长与自主工作调研结论

日期：2026 年 10 月 15 日。本文提出重写方向，具体机制与实现继续由双方讨论。

## 总体判断

Sagitta 值得沿着任务、成长、异步执行和监管四项能力重写。最有价值的变化，是让长期委托持续存在，让执行有可核查的结果，让经验能经过后续任务检验。插件数量和角色数量应随这些需求确定。

运行恢复、目标保留和资源边界可以通过工程机制加强；停滞处置和经验复用也有值得验证的方法。对于抽象目标的理解、开放任务的完成判断、跨领域经验的正确提炼，现有证据支持改进的可能性，尚不足以支持无人干预下的普遍可靠保证。模型能力仍是关键条件。

建议采用四个方向：

1. **成长采用经过验证的经验学习。** 保留事实与案例，提炼有适用条件的管理策略，在新任务上检验并修正。普通 API 模型适合先走这条路线。
2. **任务机制持有长期委托和多任务编排。** AI 动态发现工作、选择策略；程序维护承诺、资源边界、历史和完成流程。
3. **监管观察进度证据并触发纠偏。** 运行、思考、等待、休眠都有合理位置，空转和过早收口需要显式处置。
4. **异步执行提供统一、持久的工作记录。** Codex 等执行 AI 作为适配器接入；主 agent 保留直接使用简单工具和理解结果的能力。

用户希望比普通 Codex 更可靠，这个目标应落在长期委托的管理效果上：漏掉的责任更少、过早完成更少、空转更短、返工更少、人工接管更少。Codex 官方已有长程实验和持久 Goal；用户经历中的失败仍说明这些入口与实际可靠交付之间存在距离。Sagitta 的优势需要在同类任务、权限和预算下证明。[Codex 长程实验](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)、[Goal 工作指南](https://developers.openai.com/blog/mastering-codex-remote-for-engineering)。

## 长期成长应怎样实现

### 对文字经验的判断

“保存记忆就会成长”缺少充分依据；“文字载体使成长不可能”同样过强。模型的选择会受到上下文影响，经验经过抽象、筛选和反馈，可以改变后续行为。ExpeL 和 ReasoningBank 给出了这类实验依据，效果仍限于研究中的任务。[ExpeL](https://arxiv.org/html/2308.10144)、[ReasoningBank](https://arxiv.org/html/2509.25140v2)。

真正需要区分的是：系统能否在一个新情境中，运用过去形成的方法，作出更好的选择。能答出“上次发生什么”测的是回忆；面对不同项目仍能避免同类决策错误，才更接近用户期望的成长。

“非参数微调”可以作为行为效果的类比。外部经验改变模型当次的条件输入，权重保持不变；这种机制与参数训练在容量、泛化、成本和持续性上都有差异。评估应落在行为收益，避免用术语代替效果。

### 建议形成的学习过程

**经历自动留下，经验有选择地提炼。** 工具调用、委派、产物、验证、用户纠正、返工及目标变化由系统记录。任务告一段落、出现实质失败或收到新反馈时，后台产生经验候选。主 agent 少写一条记录，也能保留工作的事实；整理过程使用可观察的动作、结果与简明决策理由。

**学习内容围绕管理判断。** 优先学习如何理解用户意图、识别欠明确目标、选择执行者、设计验证、决定何时换策略和何时询问。某个仓库的路径、工具参数属于事实或操作知识；跨项目有效的派单和验收方法属于更高层的经验。具体案例支撑抽象方法，防止抽象成“认真思考、做好验证”一类泛话。

**每条经验保留条件、依据和反例。** 例如，“独立模块可以并行派单”需要同时保留“共同修改同一接口时先统一约定”的条件。一次成功只能形成有限的支持；同一经历的多次复述仍是同一份证据。失败也可能源自环境、需求变化或执行器，因果归纳应允许未知。

**由运行时在决策点提供经验。** 开始处理委托、选择执行者、遇到停滞和准备验收时，系统按当前情境提供少量相关经验与来源；AI 仍可主动搜索和展开原始案例。检索可结合任务、项目、时间、决策类型、关键词和语义相关性。向量相似度只负责部分候选选择。

这能减少“AI 忘了读写”的影响。经验进入上下文后是否被正确理解，依然需要通过后续选择和结果观察；强制它宣称“已阅读”只能证明多了一句声明。

**候选经验通过后续使用逐步取得地位。** 初始内容可以参考；在新任务上表现更好、且有可信结果支持的策略得到优先提供。出现反例、环境变化或负迁移时，缩小适用范围、降级、替换或撤回。版本和来源应保留，便于恢复旧经验集合。ACE 对局部增量维护的研究有参考价值，同时指出反思能力不足会使内容有害。[ACE](https://arxiv.org/html/2510.04618v1)。

成长评估要比较固定基础模型在“使用经验”和“移除经验”时的表现，并重测早期能力。外部记忆也会发生干扰：检索污染、经验争抢上下文和错误迁移都可能使系统退步。[经验迁移研究](https://arxiv.org/html/2604.27003v1)、[LifelongAgentBench](https://arxiv.org/html/2505.11942v3)。

### 一个管理经验的例子

用户说“优化网站”。一次失败经历是：AI 立即选择自己熟悉的重构，改了很多文件，用户仍觉得网站没有改善。

值得形成的候选方法是：当“优化”的目标维度未明确时，先检查运行证据、实际使用路径和已有约束，找出影响较大的问题；用低成本观察或可逆原型缩小不确定性，再投入实现。若维度涉及用户独有偏好、环境里也缺少线索，则保留待询问问题。

后续换成“优化部署流程”，若它能先测量失败和等待发生在哪里，选择有依据的改进，并减少返工，这才为该方法提供了新支持。重复讲述网站案例只能说明案例被记住。

### 更接近内部学习的路线

| 路线 | 能改变什么 | 对当前 Sagitta 的判断 |
| --- | --- | --- |
| 原始记忆与 RAG | 补充事实和历史案例 | 作为基础设施，单独不足以承担成长目标 |
| 经过反馈的经验、方法与技能积累 | 改变上下文中的策略选择与工作习惯 | 当前最适合验证的主路线；需要迁移测试与撤回能力 |
| GEPA 一类提示优化 | 搜索并比较提示策略 | 可离线提出改进，用户审查后更新系统提示 |
| SFT、LoRA 或策略训练 | 将一部分行为固化到模型参数 | 后续独立实验；需要高质量案例、训练服务及回归评估 |
| MemGen、Titans 等潜在记忆 | 改变内部状态、记忆结构或推理过程 | 涉及模型及推理服务改造，普通文本 API 接入条件不足 |

GEPA 的方法包含提出并测试提示变化；它适合协助用户审查系统改进。[GEPA](https://arxiv.org/abs/2507.19457v2)。MemGen 使用训练过的记忆模块和内部状态，其官方实现也列出了训练、模板更正和复现进展。[MemGen](https://github.com/bingreeky/MemGen)。Titans 属于新的神经记忆架构。[Titans](https://arxiv.org/html/2501.00663v1)。

LifeSkill 展示了将技能辅助下的成功吸收到参数中的方向；它使用可自动验证的任务反馈。抽象管理任务恰恰缺少同样明确的奖励，因此换成参数训练也绕不过反馈质量。[LifeSkill](https://arxiv.org/html/2606.04815v1)。

此前测得的 VPS 约 1 GiB 内存，适合作为轻量状态服务的候选。上述模型训练和内部记忆研究需要另行准备训练及推理资源。当前建议保留可迁移的学习数据和评估集，等有真实管理案例后，再比较参数训练是否值得。

### 用户审查与成长自主性的边界

经验内容可以在用户审查过的学习机制中增量更新。它们以带来源的参考内容参与决策，权限、任务注册规则、验收门槛和代码审查规则由固定系统执行。经验中的“以后跳过验收”无法取得修改系统规则的效力。

程序、核心提示词、系统规则、新增可执行工具及模型发布更新由用户审查。Sagitta 可以生成候选补丁、说明依据并提供对照结果，具体生效由审查流程控制。这一边界需要工具和服务权限落实。

## 抽象目标怎样变成长线多任务工作

### 长期委托与短期计划分别维护

长期委托保存用户原话、已知目的、授权范围、约束、预算和后来确认的变化。当前计划说明下一阶段打算做什么，可以随着观察调整。一轮对话结束、一个执行器退出、一个子任务完成，都只改变相应的局部记录。

长期委托的关闭进入专门流程：对照当前有效的委托范围检查结果，处理未完成项，给出验证依据。执行者可以提交完成候选；服务维护合法状态转换。预算耗尽、等待用户、阶段性停下和取消分别记录，防止被计为完成。

程序可以拒绝缺少依据、仍有未处理责任或越权的完成请求；它无法仅凭一个字段判断“这个优化确实满足了用户”。语义判断仍需运行结果、相对独立的检查及必要反馈支持。即使加入评审模型，相关错误仍可能被共同漏掉。

AI 可以细化阶段验收和修改计划，用户提出的要求与授权变更保留原始依据。为了宣布完成而删除要求、降低标准的操作应受权限约束。欠明确目标的暂定理解需要保留推测性质，无法确定的关键价值取舍继续作为未决问题。

### 目标欠明确时先开展有边界的探索

长期自主工作允许逐步形成计划。接到“优化项目”后，先查看现状、观察问题、形成少量候选方向，并区分已知约束与当前推测。接下来优先选择能降低关键不确定性的观察或实验，再决定实现任务。

计划扩展需要同时保留选择依据和阶段边界。环境证据能够揭示隐藏的必要工作；无法从证据推出的用户价值取舍，需要保留不确定性。LHAW 的研究也表明，欠明确任务涉及发现缺失信息和何时澄清，复杂计划提示的收益并不稳定。[LHAW](https://arxiv.org/html/2602.10525v1)。

用户离线时，可继续开展范围内的独立工作。涉及关键偏好、缺失授权或难以撤回的决策时，相应分支等待；其他可推进任务继续。让模型自动写一份巨大的“完整需求”，再严格完成它，可能把最初的猜测变成整夜执行的错误方向。

### 派生任务需要有目的并接受筛选

每个新任务应能回答：它服务哪个委托、由什么观察触发、预期改变什么、怎样知道值得继续。必要修复、验证与探索可以在既定授权内派生；新增独立方向进入建议或候选池，按用户给定的自主范围处理。

任务系统负责依赖关系、优先级、并发额度和待办重审。调度同时考虑用户优先级、截止时间、阻塞关系、成本和等待时长。可执行任务应定期得到重审机会；单个热门任务需要有投入边界，防止长期占满资源。所有任务同时推进会放大切换与协调成本。

活跃工作视图只展开当前需要的少量内容，其余内容按需查询。已完成、取消、合并和搁置的任务进入档案，保留结果与原因；过时的自派任务可以按规则淘汰。用户委托的责任变更需要相应权限，避免用“清理任务”悄悄缩减承诺。这直接处理此前“任务越积越多，清不掉也无法全清”的问题。

跨轮承诺、长期投入和委派适合进入任务注册。普通聊天与单次小动作可留下事件记录，发展成持续工作时再登记；这是减少噪声与保留灵活性的建议，具体注册边界仍需讨论。

### 多任务管理怎样从下层 AI 获益

Sagitta 负责理解、拆分、选人、整合和验收；下层 AI 获得相对独立的任务、必要上下文、交付要求及资源边界。不同执行器按实际擅长的工作选择。

可独立调查、独立模块实现和特定结果核查适合并行。强依赖的设计决策、同一文件的冲突修改和需要全局权衡的问题，适合先统一判断，再分配执行。受控研究发现，多 agent 的收益高度依赖任务结构，协调也会造成退步。[Scaling Agent Systems](https://arxiv.org/html/2512.08296)。

管理者需要足够的领域理解，才能识别报告中的漏洞。它可以把复杂实现交给 Codex，也可以自己执行克隆、查询和已知简单操作。遇到超出判断能力的问题，应有升级到更强模型或专门核查的途径。仅靠较弱模型统领更强执行器，无法自动获得可靠的管理能力。

对执行者的认识也可以成长：记录模型与工具版本、工作类型、实际交付质量和成本，逐步改进选人。新模型先以小规模真实任务建立能力依据；新版本上线后重测旧经验，避免把过去的工具局限当作永久规则。

## 监管怎样支持有效自主推进

建议保留监管，将其职责收敛为观察、唤醒和纠偏。任务系统决定承担什么及怎样分配工作；监管检查这些责任是否在按规则运行。

| 观察到的情况 | 合理反应 |
| --- | --- |
| 仍有可执行责任，主 agent 一轮结束后无人接手 | 恢复管理回合，要求选择下一步或给出可核查的等待原因 |
| 执行器失联、心跳中断或运行超时 | 先核对实际执行状态，按重试与取消规则处理 |
| 相同假设、操作和环境反复出现，缺少新信息 | 触发停滞复核，换诊断方法、执行者或缩小问题 |
| 有新产物但缺少验证，执行器宣称完成 | 转入验收，仍保留原委托 |
| 在分析关键问题，或实验需要合理时长 | 允许有边界的思考与观察，按预期检查点复核 |
| 等待外部结果、时间条件或用户决定 | 记录唤醒事件或复查时点，降低无效轮询 |
| 预算或截止时间到达 | 保留成果和剩余责任，进入对应的结束原因 |

进度证据可以是产物改善、验证通过、发现新事实、排除一个重要假设或解除阻塞。代码行数、消息数量、token、工具次数和进程心跳，都不足以单独证明工作有效。

停滞检测也会误判。例如同一测试反复运行可能是在验证不同修复。判断需要结合输入、代码版本、环境变化和结果。思考阶段可以简述正在区分的问题及下一项验证，系统无需保存或检查模型完整的内部思维过程。

一次停滞告警应带来策略变化，后续再次卡住则升级处置或转换工作。无新证据时重复发送“继续努力”，会把失败延长。纠偏预算应贯穿整个委托，防止靠创建新子任务不断重置。

休眠属于资源调度能力：当前缺少有价值的可执行动作时，系统记录仍承担的责任、等待依据和醒来条件。它可以全天待命，在有价值工作出现时持续执行；整夜保持高调用量并非合适的成功标准。

“人不会跑偏，AI 完全无法自纠”的判断需要修正。人也会受错误假设影响；AI 在一些可检验任务上能够自我修正，但一般开放任务中的可靠性仍有限。Sagitta 应把环境反馈和重新观察放在纠偏中心。[自我纠错研究](https://arxiv.org/html/2606.23196v1)。

## 异步执行与基础设施

### 执行层应提供的事实

派单意图先持久保存，再交给执行端。每次运行具有稳定标识，能关联委托、尝试、执行环境和产物。接收、开始、活跃、结束、结果可取以及验收通过分别有记录。执行端的最后一句“完成了”只构成报告。

重启或网络中断后，系统先核对已发工作的真实状态。可以安全重试的动作自动重试；外部副作用状态不明时先查证，避免重复发布或重复创建资源。可靠执行框架仍要求幂等和状态核对，取消也需要执行端配合。[Temporal 执行生命周期](https://docs.temporal.io/activity-execution)、[重试与幂等](https://docs.aws.amazon.com/durable-execution/patterns/best-practices/idempotency/)。

主 agent 与执行端都应能从持久记录恢复。工作上下文保留原始记录的查询入口，当前会话仅装载必要摘要；压缩后的摘要出现遗漏时，可以回到来源核对。会话、推理和执行环境分离已有一手工程实践。[Managed Agents](https://www.anthropic.com/engineering/managed-agents)。

### 对旧插件的建议

| 旧职责 | 重写方向 |
| --- | --- |
| memory 中的任务工具、注册与门禁 | 迁入任务能力；多任务编排也归任务 |
| memory 的长期记忆 | 扩展为经历、经验与反馈闭环；检索作为其中一环 |
| auto-advance | 收敛为监管、唤醒和停滞处置，与任务调度分工 |
| async-work | 形成统一执行记录与生命周期，适配官方后台能力及跨重启差距 |
| codex-dispatch | 作为可选执行器适配器，提交产物和运行事实 |
| manager、部署与更新 | 基础连接与运维独立维护，优先使用官方接口和配置 |
| 人格 | 首轮放入稳定交互原则与个人经验，后续按真实需求扩展 |

验收和评估是横跨任务、执行与成长的共同能力，首版应有明确归属。逻辑上需要这些边界，物理上可以先放在少量插件和一个共享状态服务中。

轻量 VPS 可优先验证单个状态服务、SQLite 和有节制的定时检查；耗资源的代码执行与浏览器交给其他设备或服务。DSH 的官方接口承担模型会话、插件和已支持的后台能力，Sagitta 补上长期责任及持久执行差距。具体运行版本与资源用量以原型验证确定，当前无须因为研究引用了 Temporal 或 LangGraph 就引入对应平台。

自动更新应更新到可追溯的代码、依赖和配置组合，并有回退依据。Sagitta 核心变更仍走用户审查；底层 DSH 升级也要经过兼容验证，防止官方更新改变任务或运行语义。

## 人格与个人成长

首轮人格可以落在稳定的交流习惯、对用户的了解和独立判断上。私人对话中的明确偏好、重要经历及后续变化能够纳入记忆；从中推测的性格或价值判断保持可修正。私人内容按当前工作的需要提供给执行者。

事实判断、价值偏好和工作决策分开处理：用户可以决定产品方向和投入取舍；事实问题依据证据，出现分歧时说明理由与代价；用户提供新证据后，AI 能相应修正。单纯增加反对次数，同样会损害合作。

个性化学习如果只追求“用户喜欢这次回答”，可能把迎合逐步固化。应分别观察事实判断是否稳定、是否正确理解偏好、是否愿意在证据变化时更新。[反迎合研究](https://arxiv.org/html/2310.13548)。

## 验证顺序与继续讨论的依据

首先把用户实际遭遇的失败做成样例：总目标被小任务替代、执行一半宣称完成、在同一问题上整夜重复、任务堆积、子任务结果未回流。加入需求欠明确、执行器虚报、目标调整和跨重启场景。完整说明见 [验收方案](evaluation-plan.md)。

第一轮比较固定模型的普通循环与加入任务、持久执行、完成流程后的系统；随后比较原始记忆和经验学习，最后检验选择性多 agent 是否带来额外收益。模型升级时重跑相同样例，让可由新模型承担的复杂机制有机会简化。

可信的运行约束可以先做成确定性测试；意图理解、管理判断和成长需要新情境、多次运行及少量校准过的人工抽查。用户只需优先审查系统规则、代表性分歧和异常，无须逐条确认所有记忆。

我的最终建议是：先确立长期委托、执行证据和验收的关系，再建立可以实验、撤回的经验学习。两者一起提供 Sagitta 的长程特色。潜在记忆、参数固化和更丰富的人格保持独立研究入口，等真实任务数据表明它们能解决当前路线的具体瓶颈后再加入。

本轮完成的是证据核查与方案结论，尚未运行 Sagitta 原型或管理模型对照实验。下一步应先讨论本文的机制取舍，再确定实现接口。[证据记录](evidence-ledger.md)保留来源版本、限制及未采用的结论。
